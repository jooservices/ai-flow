## Your task: prepare the release {version} (you are the developer of a Release ticket)
The release branch `{branch}` was cut from the integration branch; its pull request will target `{base}` (production). Last release tag: {last_tag}. The owner always approves a release before the merge, so your job is to prove it is good and to prepare its documents.
1. Read the ticket. List what is released: `git log {last_tag}..HEAD --no-merges --format=%s` (the whole history when there is no tag) and read the Jira tickets named at the end of the headers with `{root}/scripts/jira view <KEY>`.
2. Run the full check of the repository: {release_check}. If none is configured, use the repository's documented full test command and its end-to-end tests (README, AGENTS.md, Makefile, CI workflow) through the shared runtimes. Do NOT write new test suites for the release and do NOT change code to make a check pass: tests are written in the feature tickets, you only run them and read the result. If the repository has no way to run a full check, finish with `RESULT: BLOCKED: no full test script`.
3. If any check fails: for EVERY distinct failure create a Bug ticket in Backlog with `{root}/scripts/jira create --project {project} --type Bug --summary "<the failure>" --description-file <file under {root}/.tmp> --labels release-qa` (description: how to reproduce, the command, the output, the commit or ticket that probably caused it) and link it with `{root}/scripts/jira link --type Blocks <BUG> {key}`. Then finish with `RESULT: BLOCKED: Release QA failed, bugs: <the keys>`. Nothing is documented or committed in this case.
4. If everything passes, prepare the documents on this branch: the changelog (`CHANGELOG.md`: a new section for {version} with today's date, built from the commit headers and their tickets and grouped as Added, Changed, Fixed; keep the older sections), the README where behaviour, installation or compatibility changed, and the version in the manifests that already carry one (`composer.json`, `package.json`, `pyproject.toml`...). Commit: `chore(release): Prepare {version} ({key})`.
5. Do not tag, push, merge or rebase (the supervisor tags after the merge). Keep the branch as it is: it contains the integration branch on purpose.
6. Post the final comment in the template (What's changed = the documents and the result of every check you ran, Deployment = steps needed to ship the release).

Finish your last message with these lines:
- `PR_TITLE: chore(release): Release {version} ({key})`
- exactly one of `RESULT: DONE` or `RESULT: BLOCKED: <reason>`.
